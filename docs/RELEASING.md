# نشر إصدار تجريبي خاص

المستودع وملفات APK خاصان. لا تغيّر مستوى الوصول، ولا ترفع مفاتيح التوقيع أو رموز GitHub أو الرسائل أو الكشوف أو ملفات اعتماد التتبع الشخصية.

1. ارفع `versionCode` عن أعلى إصدار منشور، وحدّث اسم النسخة. ابنِ المرشح من التزام محدد، برسالة تتضمن `[device-test]` لرفع مرشح APK الخاص من CI.
2. انتظر نجاح الحسابات والبناء وLint واختبارات المحاكي على نفس التزام المصدر. اختبارات Android مخصصة لمحاكي مستقل وتمسح بيانات التطبيق التجريبية؛ لا تشغّلها على جوال المستخدم.
3. نزّل المرشح وبصمته وهوية مصدره. وقّعه بنفس المفتاح المحلي المستخدم لأول نسخة. لا يكفي مفتاح debug المتغير الذي ينشئه CI لكل بيئة. فقد مفتاح التوقيع يمنع التحديث المعتاد بنفس هوية التطبيق.
4. تحقق من هوية الحزمة ورقم البناء والصلاحيات والمحاذاة والتوقيع وبصمة SHA-256. إعادة التوقيع يجب ألا تغيّر محتويات التطبيق نفسها. افصح عن فجوات الجهاز الفعلي ومطابقة كشف البنك.
5. أنشئ إصدار GitHub تجريبياً خاصاً كمسودة، وارفع APK وملف البصمات، ثم تحقق من بصمة الملف المرفوع قبل نشر المسودة. لا تضمّن أي رمز دخول في رابط التنزيل أو الوصف.

لكي يكتشف التطبيق الإصدار، يجب أن يحتوي وصف الإصدار على سطر واحد حرفياً بهذا الشكل، مع القيم الفعلية:

```text
SAB_VISA_UPDATE_V1:{"packageName":"com.sabvisa.local","versionCode":3,"versionName":"0.1.0-beta.2","apkName":"SAB_Visa-0.1.0-beta.2.apk"}
```

الأرقام والأسماء أعلاه مثال اصطناعي وليست إصداراً متاحاً. يجب أن يطابق `apkName` ملف APK المرفوع، وأن يكون الوسم مثل `v0.1.0-beta.2`. يستبعد التطبيق المسودات والملفات غير المكتملة والأرقام المساوية أو الأدنى، ويفحص أحدث 20 إصداراً من المستودع المحدد فقط. افتح صفحة الإصدار بعد النشر وتحقق من الملفات والبيانات الوصفية ومن بقاء المستودع خاصاً.

فحص الإصدار داخل التطبيق يستخدم رمز قراءة مقيداً يدخله المستخدم على جواله ويُحفظ مشفراً. لا تنقل اعتماد GitHub الخاص بأدوات التطوير إلى التطبيق. الربط اختياري، وتظل معالجة SMS والحسابات محلية عند غيابه أو انقطاع الإنترنت.
